# FINAL PROJECT BRIEF — DAR AL-TIFL AL-MUSLIM ACADEMY MANAGEMENT SYSTEM

### (Enhanced Edition — with added architectural, operational & cultural insights)

> **How to read this document:** Your original brief is preserved in full and reorganized for clarity. Wherever I identified a gap, risk, or opportunity that experienced teams building similar systems (school ERPs, madrasa management platforms, SaaS scheduling systems) typically run into, I've added a **💡 Insight** callout directly under the relevant section. A completely new section (§33) at the end collects the strategic additions that didn't fit neatly into your existing numbering, so nothing you wrote is lost or reordered awkwardly.

I want to build a complete, professional, real-world digital platform for managing Dar Al-Tifl Al-Muslim and its Quran memorization circles. This must **not** be a simple informational website or a static data display — it must be a complete administrative and educational management system connecting:

**ADMINISTRATION ↔ SHEIKH ↔ STUDENT ↔ PARENT**

The entire system must be interconnected, secure, scalable, responsive, and based on a real database so that all information and operations are permanently stored and never lost.

---

## 1. BRAND IDENTITY & UI/UX DESIGN

- Official name: **Dar Al-Tifl Al-Muslim**. Use the attached logo without modification, on the login page, dashboard, sidebar, and main pages.
- Modern, professional Islamic and educational identity suitable for children and young students.
- Harmonious color palette inspired by the logo; clean, highly readable Arabic fonts.
- Full Arabic RTL support throughout.
- Clean, elegant, uncrowded UI with consistent iconography.
- Careful attention to micro-states: buttons, tables, cards, modals, notifications, loading states, empty states, success/error messages.
- Fully responsive across desktop, tablet, mobile.
- Restrained animation — the system should feel like real software, not a demo.

> **💡 Insight — Bilingual and mixed-direction support**
> RTL Arabic is correctly the priority, but plan the CSS architecture (logical properties: `margin-inline-start` instead of `margin-left`, etc.) so an English or French interface toggle can be added later without a rewrite — many parent bodies include non-Arabic-literate guardians, and government/partner reporting is often required in a second language. Also decide *now* whether numerals display as Arabic-Indic (٠١٢٣) or Western (0123) per field — dates, phone numbers, and currency often need to stay Western-numeral even in a fully Arabic UI for readability.

> **💡 Insight — Design for a child-and-parent audience, not just admins**
> Most Quran-academy software is designed around the admin's convenience and the student/parent experience is an afterthought. Since children as young as 5–6 may use the student dashboard, consider a simplified "child mode" (large buttons, minimal text, progress shown visually as a filling Mushaf/Juz bar) with a separate, denser "parent mode" for guardians who want detail.

## 3. ACCOUNT REGISTRATION & LOGIN SYSTEM

Self-service registration (name, phone, account type, password/confirm password), phone number as the primary login credential (no mandatory email). New accounts start as **PENDING APPROVAL** and only become **ACTIVE** after admin review; admin can also **REJECT**, **SUSPEND**, or **REACTIVATE**.

> **💡 Insight — Phone-based auth needs a fallback and abuse controls**
> Phone-number-as-username is the right call for this region/audience, but build in from day one:
>
> - **OTP verification via SMS/WhatsApp** at registration to confirm the number is real and reachable — this also prevents fake/duplicate account spam clogging the approval queue.
> - **Account recovery flow** for a lost password when there's no email: typically OTP-to-phone + a manual admin-assisted reset as a last resort.
> - **Rate limiting on login attempts** (e.g., lockout after 5 failed attempts) since phone numbers are easier to guess/enumerate than emails.
> - Decide how you handle a **changed phone number** (very common) — this should be a formal, audited "change request" flow, not a silent self-edit, since phone number *is* the login identity.

## 4. ACCOUNT REQUEST MANAGEMENT

Dedicated "Account Requests" dashboard section listing all pending/approved/rejected/suspended requests with full detail, and admin actions to approve/reject/link/suspend/reactivate.

> **💡 Insight — Prevent approval-queue bottlenecks**

> - **SLA indicators** — flag requests pending longer than 48/72 hours in a different color, since delayed approval directly hurts enrollment conversion.
> - **Delegate approval rights** to a secondary admin/registrar role so one person isn't a single point of failure.

## 6. PARENT ACCOUNT & CHILDREN LINKING

One parent account can be linked, post-approval, to multiple children; each child's data stays fully separated; a parent can never see unlinked students.

> **💡 Insight — Plan for family complexity**
> Real families are messier than "one parent, N children":
>
> - **Two guardians per child** (e.g., father and mother each want independent login access to the same child) — model this as a many-to-many `parent_student` relation, not one-to-many, from the start; retrofitting this later is painful.
> - **Guardianship changes** (custody changes, a child transferring to a relative's care) should go through the same audited request flow as initial linking.
> - Consider a **per-guardian visibility flag** if the academy ever needs to restrict what one linked guardian can see relative to another (e.g., financial info only visible to the paying guardian).

## 7. USER ROLES & PERMISSIONS (RBAC)

Four roles — **Administration, Sheikh, Student, Parent** — each scoped exactly as you specified (Sheikh limited to assigned circles; students/parents limited to their own data).

> **💡 Insight — Design permissions as granular and role-*****and*****-record scoped**
> Two refinements that pay off as the system matures:
>
> 1. **Split "Administration" into sub-roles** (Super Admin, Registrar, Accountant, Content Editor) even if you launch with one person wearing all hats — a flat, all-powerful admin role is a common security and operational weak point once staff grows. Financial data in particular (§15–17) often needs to be restricted to a bookkeeper role, separate from academic administration.
> 2. **Row-level, not just page-level, permission checks** — a Sheikh's access must be enforced at the *database query* level (only circles/students explicitly assigned to them), not just hidden in the UI. A determined user changing a URL parameter or API call must still be blocked server-side.

## 8. STUDENT PROFILE

Personal, educational, and financial information plus a full chronological **student timeline** from day one (attendance, memorization, revision, assessments, results, notes, level changes, circle transfers, payments).

> **💡 Insight — The timeline is your most valuable long-term asset; protect it**
> This timeline effectively becomes each child's Quran-memorization "permanent record" — potentially spanning a decade. Two additions:
>
> - **Immutability**: timeline entries should never be hard-edited after the fact; corrections should append a new entry referencing the old one (audit-safe), matching your Soft Delete philosophy in §24.
> - **Exportable "memorization certificate" / progress report**, generated from the timeline, that a family can download or print for scholarships, other institutions, or personal keepsake — this is a small feature with outsized emotional and practical value for families.

## 33. ADDITIONAL STRATEGIC CONSIDERATIONS *(new section)*

These didn't map cleanly onto your existing numbering but are worth deciding before development starts, since each is far cheaper to plan for now than to retrofit:

**Cultural/calendar fit**

- Support the **Hijri calendar alongside Gregorian** throughout (schedules, birthdates, reports) — a small addition that meaningfully increases trust and usability for an Islamic institution.
- Build a **Ramadan schedule mode**: many Quran academies shift circle times and intensify memorization targets during Ramadan; a toggle that lets admin temporarily override normal schedules (and reverts cleanly afterward) avoids a month of manual workarounds every year.
- Consider whether prayer-time-aware scheduling (avoiding session conflicts with Maghrib/Isha, common class times) is worth a lightweight prayer-time API integration.

**Technical architecture**

- Pick a stack with a **real relational database** (PostgreSQL or MySQL) given how relational this data model is (many-to-many parent/student, Sheikh/circle, financial ledgers). A NoSQL-first approach would fight you constantly here.
- Plan for **multi-branch/multi-campus** support even if launching with one location — academies of this kind frequently expand, and "which branch" is much easier to add as a first-class field now than as a retrofit.
- Define a **notification queue/worker** architecture early (rather than sending SMS/WhatsApp synchronously in request handlers) so message sending never blocks or breaks core actions like attendance recording.

**Operational realism**

- Add a **staff onboarding/offboarding checklist** built into the Sheikh account lifecycle — what happens to a departing Sheikh's assigned circles, historical attribution, and outstanding dues.
- Budget realistically for **ongoing costs**: SMS/WhatsApp API fees scale with student count, hosting/backup costs scale with data volume (photos and documents especially), and someone will need to own approvals/moderation as an ongoing operational role, not a one-time setup task.

**Testing & rollout**

- Given the number of interdependent modules, plan a **phased rollout**: e.g., Phase 1 = registration, approval, circles, attendance; Phase 2 = memorization/revision/assessments; Phase 3 = finance (salaries/subscriptions/payments); Phase 4 = messaging/reports/public site polish. Trying to launch all 30+ sections simultaneously is a major delivery risk.
- Treat the three flows in §25 (plus the two added above) as your **integration test suite** — if an AI or developer builds each module in isolation without validating these flows end-to-end, "interconnection" will quietly fail even though every individual page looks correct.
